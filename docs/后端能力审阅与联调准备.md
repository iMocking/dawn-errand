# 后端能力审阅与三端联调准备

> 审阅对象：`dawn-errand` 后端（Go 1.27 · Gin · ent · Casbin · PostgreSQL 16 · Redis 7）
> 审阅时间：2026-10-25
> 判定口径：以「用户端 / 商家端 / 骑手端能否真实跑通业务闭环」为标准，而非「管理后台是否可用」。
> 配套文档：[三端联调接口契约（v0.1 草案）](三端联调接口契约.md)
>
> **更新（2026-10-25）**：M0（会话/账号/上传）、M1（菜品目录/地址簿/营业设置）、M2（下单/支付/接单/取送/确认）、M3（位置追踪/通知/超时任务）、M4（钱包/提现/评价/售后）、M5（优惠券/支付回调/对账/运维手册）已落地，最新状态见 [后端商用化完善计划](后端商用化完善计划.md) §14。本文保留为缺口基线与验收依据；「三端接口 0 条 / 账号 0 个」等描述对应 M0 之前的状态。

## 1. 结论摘要

后端目前是一个**「平台运营后台 + 统一身份认证」后端**，不是「交易平台后端」。

- **已经可商用**：管理后台的读接口、商家/骑手审核、提现审核、配置管理、JWT 会话与 RBAC、审计、指标。后台侧 39 条业务路由 + 16 条超管配置路由均已实现（既有集成测试与本次抽测通过）。
- **三端业务能力为 0**：商品目录、地址簿、下单、支付、接单、取货、送达、评价、钱包、结算这些**领域本身不存在**（不是缺接口，是缺表、缺聚合、缺用例）。
- **账号开通链路断裂**：管理端创建商家/骑手不会创建可登录账号，也不写 `owner_user_id` / `user_id`；数据库当前 18 个用户中**没有任何 `merchant` 或 `driver` 角色账号**（13 user + 4 system + 1 super_admin）。
- **短信登录存在会话层阻断（已实测复现）**：`POST /api/auth/sms/login` 返回 200 且带 token，但随后任何需登录接口都返回 `401 / code=1006「登录状态已失效」`。原因见 §4.1。用户端目前唯一接入的真实链路因此不可用。

> 缺口计数：**P0 阻断 8 项**（§4）、**P1 完整性 12 项**（§5）、**契约冲突 10 项**（§6）、**工程质量风险 11 项**（§7）。
>
> 阅读顺序建议：三端负责人先看 §1/§4/§6，再评审 [契约文档](三端联调接口契约.md) §2–§5；后端按 §9 的 M0–M4 推进。

三端就绪度：

| 端 | 真实后端能力 | 主要阻断 | 联调就绪度 |
|---|---|---|---|
| 用户端 `apps/client` | 短信/邮箱登录、实名认证、本人订单只读 | 短信登录会话断裂、无商品/地址/下单/支付/追踪 | 登录 50%，业务 0% |
| 商家端 `apps/store` | 邮箱登录、本店订单只读 | 无商家账号、无菜品、无接单/营业设置、无结算 | 0% |
| 骑手端 `apps/driver` | 邮箱登录、本人订单只读 | 无骑手账号、无抢单池、无定位/取送、无收入 | 0% |
| 管理后台 `apps/admin` | 全量 | — | 可用 |

## 4. P0 阻断项（不解决则三端无法联调）

### 4.1 短信登录会话断裂（实测复现，优先级最高）

**现象**：`/api/auth/sms/login` 成功后，携带返回的 access token 访问任何需登录接口，一律 `401 / 1006「登录状态已失效，请重新登录」`。

**根因**：`middleware.Auth()` 在每次请求都要求存在 `credential` 行并与 `session_version` 比对（`internal/interfaces/middleware/middleware.go:157-163`）；而 `autoRegisterByPhone()` 只写了 `users` + `user_profiles`，**没有创建 `credentials` 行**（`internal/application/auth/service.go:330-357`）。`issueTokens()` 在无凭证时把 `sv` 当 0 签发（`service.go:360-364`），于是签发成功、校验必败。

**连带影响**：

- 已存在的「无密码用户」（如种子用户 `U86540 王秀兰`，手机号 `13800008640`）短信登录后同样 1006。
- `POST /api/auth/refresh` 对这类用户直接返回 `401 凭证不存在`（`service.go:402-405`）。
- 用户端 `apps/client` 的**唯一真实链路**（短信登录）实际不可用，`docs/客户端交付说明.md` §7.2 的「真实短信登录成功」只验证了登录响应，没有验证后续鉴权。

**修复建议**（小改动、高优先）：

1. `autoRegisterByPhone` 事务内补建 `Credential{UserID, PasswordHash:"", SessionVersion:0}`；或
2. 在 `issueTokens` 中「无凭证则创建初始凭证」；并让 `refresh` 对无密码用户允许续期；
3. 补集成测试：短信登录 → `/auth/me` → `/orders` → `/auth/refresh` 全链路（现有 17 个用例未覆盖）。

> 同类问题：短信自动注册未写 `region_id`，所有按区域过滤的 C 端查询都会为空（见 §4.8）。

### 4.2 商家/骑手账号开通与主体绑定缺失

**证据**：

- `MerchantsService.Create` 只写 `merchants` 表，不创建用户、不设置 `owner_user_id`（`application/admin/merchants.go:99-131`）。`merchants.owner_user_id` 字段存在但全仓库无写入点（`ent/schema/business.go:19`）。
- `RidersService.Create` 只写 `riders` 表，不设置 `riders.user_id` 与 `users.rider_id`（`application/admin/riders.go:102-131`）。
- 数据库实测：`merchant` / `driver` 角色账号数为 **0**。商家端只能用 `user` 角色登录（`docs/商家端交付说明.md` §8.3 已记录此现象）。
- `middleware.Auth` 从 `users.merchant_id` / `users.rider_id` 派生 Scope；绑定为空时 `scopeOrder` 会过滤 `merchant_id=''` / `rider_id=''`，查询结果恒为空——**表现为「什么都查不到」，且把配置错误掩盖成空列表**。应在中间件层直接拒绝并返回明确错误码。

**影响**：商家端/骑手端无法以正确角色进入，所有按主体隔离的查询/操作都不可用。

**修复建议**：

1. 新增「开通账号」用例（事务）：创建/绑定 `user`（role=merchant|driver）+ `credential` + `users.merchant_id|rider_id` + 主体表反向 `owner_user_id|rider.user_id`；
2. 管理端入口：`POST /api/merchants/:id/account`、`POST /api/riders/:id/account`（或创建主体时带 `owner_phone` 自动开通）；
3. 商家/骑手端增加「账号未绑定主体」的明确错误码（建议 `1202`），禁止在绑定为空时放行；
4. 补 seed：至少 1 个商家账号、1 个骑手账号，供三端联调（见契约文档 §8）。

### 4.3 商品目录（分类 / 菜品）完全缺失

**证据**：ent schema 仅 `business.go` / `cms.go` / `identity.go` 三个文件，无 `dishes`、`dish_categories`、`products` 任何表；迁移 001/002 中亦无。前端侧却有完整模型：客户端 `Dish/Merchant`（`apps/client/.../data/Models.kt`）、商家端 `DishCategory/Dish`（`apps/store/.../data/StoreRepository.kt`）。

**影响**：用户端无法浏览菜单/加购，商家端无法管理菜品，下单无商品可校验。

**修复建议**：新增 `dish_categories`、`dishes` 两表与商家端 CRUD、用户端只读菜单接口；库存/售罄用 `stock` + `on_sale` 表达，下单时服务端二次校验价格与库存。

### 4.4 收货地址簿缺失

**证据**：`user_profiles` 只有一个 `address` 字符串（`ent/schema/identity.go:155`），无地址表；客户端 `Address` 支持多地址、默认地址、标签（`Models.kt:96-107`），`DemoRepository` 已有增删改查与默认切换。

**影响**：无法选择/保存地址，下单无送达点坐标（追踪也依赖坐标）。

**修复建议**：新增 `user_addresses`（含 `lat/lng`、`is_default`、部分唯一索引保证单默认）；提供 CRUD + 设默认；下单时快照地址，避免地址后续被修改影响历史订单。

### 4.5 订单写链路与状态机缺失

**证据**：

- `OrderRepository` 只有 `Save`（Create）与查询，**没有 Update/状态流转方法**（`domain/order/order.go:137-168`）；`OrderRepo.Save` 固定 `Create()`，重复保存同 ID 会失败（`repo/order.go:23-40`）。
- 全仓库没有任何订单创建入口：`Save` 仅在 `cmd/seed` 调用，应用层无 `CreateOrder` 用例。
- 订单表是「后台展示快照」：无 `accepted_at/ready_at/picked_at/delivered_at/canceled_at`、无 `address_id`、无 `payment_status`、无 `pickup/delivery` 坐标、无 `cancel_reason`（`ent/schema/business.go:122-150`）。
- 状态枚举为后台口径：`待接单 / 配送中 / 已取件待送达 / 已完成 / 已取消 / 出餐超时 / 异常`（`domain/order/order.go:20-28`），缺少 `待支付 / 待取货 / 已送达 / 待评价 / 退款售后`；客户端与之不匹配（`apps/client/.../Models.kt:44-52`）。

**影响**：三端最核心的「下单 → 支付 → 接单 → 取货 → 送达 → 评价」链路完全不存在。

**修复建议**：

1. 订单状态机（建议保留中文入库值以兼容后台，API 额外返回英文 `status_code`，见契约文档 §5）；
2. 增加 `order_events` 事件表 + 时间戳字段，所有流转写事件；
3. 应用层新增 `OrderAppService`（创建/取消/支付回调/接单/出餐/取货/送达/确认/评价），仓储补 `UpdateStatus` 与乐观并发 `WHERE status = ?`；
4. 服务端权威计价（禁止信任客户端金额），下单幂等（`client_order_no` + 唯一索引）。

### 4.6 配送闭环缺失（抢单池 / 定位 / 轨迹）

**证据**：

- `rider` 表无经纬度、无在线位置；`order` 表无取送货坐标（`ent/schema/business.go:69-106,122-150`）。
- `driver` 角色 Scope 只过滤 `rider_id = 自己`（`repo/store.go:88-100`），而待抢订单 `rider_id=""`，**骑手永远看不到**——现有 Scope 无法支撑抢单池。
- 客户端追踪页依赖的后端契约 `GET /orders/:id/track` 尚未实现（`docs/客户端高德地图适配说明.md:97-111`；`实施进度记录.md` 已标注待实现）。
- 无 Redis GEO / 无位置上报 / 无 ETA 服务。

**修复建议**：

1. 订单增加 `pickup_lat/lng`、`delivery_lat/lng`（下单时快照）；商家表增加 `lat/lng`；
2. 新增 `rider_locations` 表 + Redis GEO（`geo:riders:<region>`）保存实时位置；
3. 新增抢单池查询（`rider_id=''` + 状态 + 区域 + 距离排序，走独立查询而非 rider scope）；
4. 抢单用单条带条件的 `UPDATE ... WHERE id=? AND rider_id=''` 保证并发安全（受影响行数为 0 → 409）；
5. 实现 `GET /api/app/client/orders/:id/track`，字段按既有建议契约，骑手位置来源为上报表。

### 4.7 商家/骑手自助操作缺失

**证据**：

- `MerchantsService.UpdateStatus` 已实现但**没有路由**（`router.go` 商家组无 status 接口）。
- `RidersService.UpdateStatus` 同样无路由；骑手上线/下线、接单、取货、送达均无入口。
- 商家无「接单/拒单/出餐」动作，无营业时间/自动接单/起送价/配送费/公告等设置项（表里只有 `open_hours`、`delivery_range`）。
- 骑手无收入流水、无钱包、无提现申请；`withdrawals` / `settlements` 只有后台读与审核（`application/admin/finance.go`）。

**影响**：即便订单能创建，商家和骑手也无法推进状态。

**修复建议**：按契约文档 §3/§4 补齐 `/api/app/store/*`、`/api/app/driver/*`，状态变更全部走订单状态机与事件表。

### 4.8 用户区域归属缺失（C 端查询会全空）

**证据**：`autoRegisterByPhone` 不写 `region_id`（`service.go:330-357`）；`user_profiles.region` 也是空。平台所有 C 端目录/商家/订单查询都按 `region_id` 做租户隔离（`repo/store.go`），空区域用户将查不到任何商家。

**修复建议**：新增 `GET /api/app/client/regions`（运营中区域）+ `PUT /api/app/client/region`；首次进入客户端时选择乡镇/区域并写入 `users.region_id`；下单前强制校验。

## 7. 工程质量与运维风险（建议随首轮改造一并处理）

1. **仓储层忽略请求上下文**：`repo/*.go` 普遍使用 `context.Background()`（如 `repo/order.go:24`、`repo/identity.go:21`），请求取消/超时无法传导到 SQL。
2. **错误比较方式**：多处 `err == application.ErrNotFound`（如 `admin/dashboard.go:117`），应统一 `errors.Is`。
3. **订单仓储缺更新能力**：只有 Create，无 Update/乐观锁；状态流转必须新增。
4. **主体绑定兜底**：merchant/driver 绑定为空时查询恒为空列表，问题被掩盖；应在中间件层直接拒绝（返回 `1202`），而非静默空结果。
5. **最小权限**：merchant 拥有 `settings:list`，可读区域/费率/公告等平台配置（`casbin.go:293-297`），建议复核。
6. **无 OpenAPI/契约测试**：后台契约靠 `mappers.go` 与前端逐字段对照；三端接入前应产出机器可读契约（可由本契约文档转 OpenAPI，或直接以代码生成）。
7. **集成测试耦合**：`internal/integration/api_test.go` 硬编码超管凭据、依赖种子数据，跑前需 FLUSHDB（`后端交付报告.md` §7.4）。
8. **Access Token 15 分钟**：三端均未实现 401 单飞刷新（客户端交付说明 §8.3、商家端 §8.4）；联调前必须补齐，否则长会话频繁掉线。
9. **存储为死代码**：`assembly.go:144` 的 `_ = storage.NewLocal(...)` 未注入任何用例。
10. **缺业务指标**：`/metrics` 只有 HTTP 维度，缺下单量、抢单冲突、履约时长等经营指标。
11. **种子数据不足**：只有 1 商家、1 骑手、1 订单、0 个商家/骑手账号，无法支撑三端并行联调。

## 8. 目标蓝图（建议）

### 8.1 接入层

新增 `/api/app` 命名空间，与后台 `/api/*` 完全隔离（后台契约零改动）：

```
/api/app/client/*   角色 user      —— 浏览、地址、下单、支付、追踪、评价、售后
/api/app/store/*    角色 merchant  —— 店铺、菜品、接单、出餐、统计、结算、提现
/api/app/driver/*   角色 driver    —— 上下线、抢单池、取送、位置、收入、提现
/api/app/common/*   任意已登录    —— 公告、上传、反馈
/api/auth/*         保持不变      —— 登录/刷新/登出/实名
```

授权采用 Casbin 新策略（`app_client:*` / `app_store:*` / `app_driver:*`）+ 主体绑定校验，数据隔离继续走 `tenant.Scope`。

### 8.2 领域与数据

新增（migration 003）：`dish_categories`、`dishes`、`user_addresses`、`order_events`、`payments`、`refunds`、`reviews`、`user_coupons`、`wallet_accounts`、`wallet_transactions`、`rider_locations`、`device_tokens`。

订单表扩展：状态时间戳、地址快照、取送坐标、费用分项、`client_order_no`、`payment_status`、`rider_earning`。

商家/骑手表扩展：`lat/lng`、经营设置（自动接单/起送价/配送费/公告），主体 ID 反向绑定。

### 8.3 状态机

见契约文档 §5。核心链路：

```
待支付 →(支付)→ 待接单 →(商家接单)→ 备餐中 →(出餐)→ 待取货
      →(骑手抢单+取货)→ 配送中 →(送达)→ 已送达 →(用户确认/自动)→ 待评价 →(评价)→ 已完成
旁路：已取消 / 退款售后 / 异常
```

### 8.4 支付抽象

先实现 `PaymentGateway` 接口 + `mock` 实现（余额 / 微信模拟），下单后调用 `POST /orders/:id/pay` 即置为已支付并生成 `payments` 行；真实微信/支付宝作为第二个实现接入，回调统一走 `/api/payments/callback/:channel`。这样三端联调不被支付资质阻塞。
