## 2. R1–R5 主计划：5 项未完成，逐项证据

### R2-4 第三方渠道订单取消后无真实退款（`[ ]`）

- **证据**：`internal/application/app/order_client.go:63` 的 `Pay` 里 `wechat`/`alipay`/`mock` 共享同一条模拟路径（`:78-86`，要 `MockPayment` 打开，非 dev 直接拒绝），余额是唯一真实扣款通道；`internal/application/app/order.go:520` 的 `cancel` 对已支付单只做两件事——`balance` 退回钱包（`:540`）、支付单标 `refunded`（`:544-548`），没有任何渠道退款调用。全仓只有 `PayoutGateway`（提现打款），没有 `PaymentGateway` 或 `Refund` 端口。
- **还差**：① 定义 `PaymentGateway.Refund(ctx, payment, reason)` 端口；② 无渠道时落「待退款工单」并告警，禁止只改标记；③ 余额路径保持现有原子退回。
- **阻塞点**：工单是新产品物件（表 + 管理端页面 + 处置流程），需要产品口径；但端口抽象与「未配置渠道时拒绝静默标记」可以先行。

### R2-5 支付回调验签在 handler 且签名 payload 不含 channel（`[~]` 验签部分已完成）

> **2026-10-26 已部分修复**：验签下沉到 `internal/infrastructure/payment`（`HMACVerifier` 实现 `application.PaymentNotifyVerifier`），待签名串改为 `channel|order_id|trade_no|amount(2位)|status|timestamp`，跨渠道重放被判签名不符；时间窗/字段完整性/未配置密钥三类错误分开映射。剩「已取消单回调落『已付未入账』异常账」待产品口径。详见 [实施进度记录](实施进度记录.md)「（二十）」。

- **证据**：`internal/interfaces/http/payments.go:41-42` 的待签名串是 `order_id|trade_no|amount|status|timestamp`，**不含 channel**；channel 在 `:54` 从路径参数取、不经签名。也就是说，为 A 渠道生成的合法签名可以原样打到 `/payments/callback/B` 上，`payment.channel` 会被记成 B。验签仍在 HTTP handler（`hmac.Equal` 在 `:46`）。
- **另一处**：`internal/application/app/order_client.go:134-136` 对「订单已取消/已完成」的回调直接返回 `CodeOrderState`，**不落任何异常账**——渠道已经扣了用户的钱，系统只回一个错误，对账靠人肉发现。
- **还差**：① 签名 payload 加入 channel；② 验签下沉到支付适配层（infrastructure）；③ 「已付未入账」异常记录 + 纳入对账处置。
- **窗口判断**：当前没有任何真实渠道接入，改动签名格式的兼容成本为零；一旦接入微信/支付宝再改，就要同时改渠道侧签名配置。**这是五项里最值得先做的一项。**

### R2-6 金额 float64 迁移（`[ ]`）

- **证据**：`internal/infrastructure/ent/schema/business.go` 里 30+ 个金额/比例字段是 `field.Float`（PG `double precision`），`migrations/004_orders.up.sql:12-15/55` 同样；R5-6 已把影响面固化成 `internal/integration/testdata/app_money_fields.txt`（41 条路径 / 14 个字段名）。
- **还差**：域模型与 DTO 改 int64 分、迁移含换算与回滚、三端解析同步发版（契约明确要求同版本发布）。
- **阻塞点**：破坏性变更 + 三端同版本，属独立里程碑，不能顺手做。

### R4-4 Android 生产 HTTPS 与存储加固（`[~]`）

- **已完成**：三端 `networkSecurityConfig`、`allowBackup=false`、基址 `-P*ApiBaseUrl` 注入（见 R4-4 记录）。
- **仍缺**：token 仍是**明文 SharedPreferences** —— `apps/driver/.../DriverApp.kt:13`、`apps/store/.../StoreSession.kt`、`apps/client/.../DemoRepository.kt:43` 都直接读写 `token` / `refresh_token`。`allowBackup=false` 只挡住云备份与 ADB，挡不住 root 设备与提权恶意应用。
- **需要拍板**：`androidx.security:security-crypto` 已不再推荐（EncryptedSharedPreferences 废弃），可选 ① Android Keystore + AES-GCM 自封装，② DataStore + 自管密钥。选定后是 0.5–1 天的活。

### R4-6 三端 ApiClient 重复与异常吞没（`[~]`）

- **已完成**：异常吞没收口、`POST→PUT` 405、短信登录假成功、`X-Request-ID` 对齐（R4-6 记录）。
- **仍缺**：三份 `ApiClient.kt`（`apps/client`、`apps/store`、`apps/driver`）仍各写一遍；三个端是**各自独立的 Gradle 工程**（各有 `settings.gradle.kts` 与 wrapper，均 Gradle 9.8.2；`apps/` 下没有根工程），所以「并成 `:network` 模块」必须先并 Gradle root。
- **工作量**：并根 + 抽模块 + 三端 `assembleDebug` 回归，1–2 天；纯结构改动，风险低但收益也低，建议排在 App 联调之后。
