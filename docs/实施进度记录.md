## 2026-10-26（十四）R5-1：仓储层 ctx 端到端透传，取消与超时终于能传到 SQL

- **补的是哪块洞**：`internal/infrastructure/repo/*.go` 里 163 处 `context.Background()`。仓储层自造上下文意味着请求取消、网关超时、链路追踪、优雅停机全链路在数据库这一层断掉——客户端早已断开，Gin handler 也已返回，那条 ent 查询仍在后台跑完并可能写库。资金与状态机路径上这尤其危险：超时重试叠加迟到的旧请求继续提交，就是 R1-1 那类双花竞态的温床。
- **改法（编译期驱动，不做语义改动）**：19 个领域仓储端口共 171 个方法首位加 `ctx context.Context`，`repo/*.go` 的 177 个实现同步接收并直接交给 ent（`Only(ctx)`/`All(ctx)`/`Save(ctx)`/`Exec(ctx)`），删掉实现里 `ctx := context.Background()` 兜底行；跨域的私有助手一起透传——`OrderRepo.listBefore`、`OrderService.{record,load,buildFoodOrder,applyCoupon,notify,notifyMerchant,storeOrder,driverOrder}`、`RefundService.notifyUser`、`FinanceAppService.{withdrawRule,partyInfo}`、`StoreService.{ownCategory,ownDish}`、`ClientService.ownAddress`、`deductBalance`/`creditBalance`/`creditWallet`/`debitWallet`、admin 侧 `bindSubject`，保证 `RepoUnit` 事务单元里每条余额加减与状态流转都可被取消。顺序是先手工做 wallet（资金域，逐行核对），再用脚本做其余域，每批跑 `go build ./...` 拿「not enough arguments」逐点补 ctx——这样漏改只会编译失败，不会静默改错行为。
- **装配与配置闭包**：`assembly.Build(ctx, cfg)` 收进程根上下文（`cmd/server`/`cmd/seed`/`cmd/sealidcards` 传入，`Schema.Create(ctx)` 复用同一 ctx）。`mailer.ConfigProvider` 由 `func() (*SMTPConfig, error)` 改为 `func(ctx, ...)`，`storage` 的配置闭包由 `func() *LocalStorageConfig` 改为 `func(ctx) ...`，`syscfg.SMTP/LocalStorage` 随之透传——发信前读 SMTP 配置、上传前读存储上限，这两次 settings 行读取现在也能取消。

## 2026-10-26（十二）R5-4：assembly 只留连线，运行期配置适配收进 syscfg

- **改了什么**：新增 `internal/infrastructure/syscfg/syscfg.go`，把原先长在 `internal/assembly/assembly.go:63-132` 的四段基础设施逻辑搬过去——`SMTP`（读 settings 行 → 反序列化 → 用 `crypto.Cipher` 解密密码，`******` 占位符不解密）、`LocalStorage`（读 settings → 缺失/损坏字段回落启动配置）、`Outbox`（dev 发件箱按 `created_at` 倒序取最近 N 封，N 越界回落 50）、`Ready`（数据库 `Exist` 探测 + Redis `Ping`）。`Build` 现在只做「取依赖 → 拼结构体 → 注入」，250 行降到 171 行。

## 2026-10-26（十）R4-6（上）：三端 API 层去掉异常吞没，顺带修出三个联调级缺陷

- **收口原则**：用户主动操作（登录、取验证码、接单/出餐、上下线）必须能拿到「为什么失败」；后台刷新类 GET 保持可空返回，但失败一律 `Log.w` 留痕（method、path、`code`、`httpCode`、后端 `message`、`request_id`）。三端 `request()` 不再返回 `null`——网络异常、非 2xx、响应不是统一信封（405 纯文本、网关 HTML）各自给出可判读文案；`Resp.ok = code==0 && httpCode in 200..299` 统一判定；`client` 的 `getObject` 四处静默 `null` 与 `post` 抛异常前同样补日志。driver/store 原先不发 `X-Request-ID`，现与 client 对齐自生成 UUID，并在后端未回 `request_id` 时回落到本地值——R4-3 之后服务端排障只认 `request_id`，App 不带等于放弃了这条链路。
- **修出的缺陷 1（上下线从未生效）**：`DriverRemoteRepository.setOnline` 用 `POST /api/app/driver/status`，后端是 `PUT`（`router.go:261`，`store` 同样在 `router.go:234`）→ Gin 405 + 纯文本 → JSON 解析失败 → `code=-1` → `postOk=false`，而调用方 `HomeViewModel.setOnline` 把返回值丢了，UI 开关照翻、副标题照改，骑手以为自己在接单状态。新增 `putResp`、改走 PUT，`HomeViewModel` 暴露 `statusError: LiveData<String?>`，`HomeFragment` 观察后 toast（不动开关本身，避免 `onCheckedChange` 回写造成状态抖动）。
- **修出的缺陷 2（验证码登录不持 token）**：driver 的 `smsLogin` 只返回 Boolean，从不写 `ApiClient.accessToken`（只有 `loginWithPassword` 写），`LoginActivity` 成功分支里 `accessToken?.let { 持久化 }` 因此静默跳过，登录后所有 `/api/app/driver/*` GET 走无鉴权 → 401 → 首页/财务全空白。现 `smsLogin` 返回 `Resp` 并在成功时写入 token。
- **修出的缺陷 3（把失败报成成功）**：store `sendSmsCode` 返回 `String?`（只用于 dev 验证码回显），断网、429、业务拒绝统统 `null`，`LoginViewModel` 于是显示「验证码已发送，请查收短信」——用户等一条永远不会来的短信。driver 侧对称为「验证码发送失败，请检查后端短信服务」（网络不通也怪短信服务）与写死的「验证码错误，请重试」。现两端都透传后端 `message`；driver 还修了「先起 60s 倒计时再发请求」导致失败也锁按钮的问题，改为仅成功时倒计时。store 三个订单动作（接单/拒单/出餐）返回 `Resp`，`OrdersActivity` 的 toast 从固定「请刷新后重试」改成带后端原因。
- **未合并的部分**：三份 `ApiClient` 仍是拷贝（client 走 `ApiException` 抛出式、store/driver 走 `Resp` 返回式，本轮先统一 store/driver，未改动 client 的对外形态，避免动到 4 个 `?: return` 的仓库方法）。抽 `:network` 需要把 `apps/{client,store,driver}` 三个独立 Gradle root 并成一个构建——这会改所有开发者的 `./gradlew` 执行目录与 IDE 运行配置，不属可以静默完成的改动，保留在计划项里。
- **新发现的功能未接通（记录待办，不在本任务内修）**：商家端「经营设置」整页只写本地偏好（`BusinessActivity.kt:44-127` → `StoreSettings.set*`），后端 `PUT /api/app/store/business` 从未被任何调用点使用，`StoreRemoteRepository.setOpen` 是死代码。即商家改营业时间/起送价/公告只存在于本机，换设备或重装即丢。逐控件定义服务端往返与失败语义需要设备联调验证，另列待办。
- **验证**：三端 `:app:compileDebugKotlin --offline` 全 BUILD SUCCESSFUL（driver、client、store 各一次，追加改动后复核 UP-TO-DATE）；本机无设备/模拟器，运行期行为（toast 文案、开关抖动）未验证。

## 2026-10-23（五）token 到期跳登录修复（前端自动续期 + TTL 治理）

- 问题：静止一段时间不操作，刷新页面即被踢到登录页。
- 根因审查结论：
  - 后端 access token 默认 TTL **900s（15 分钟）**（`config.go` `ACCESS_TOKEN_TTL` 默认 900；`REFRESH_TOKEN_TTL` 默认 1209600s=14 天）；
  - 后端续期接口 `POST /api/auth/refresh`（轮换 access+refresh）本就完整，登录响应含 `refresh_token`；
  - 前端断链：axios 401 拦截器直接清会话跳 /login，从不调用 refresh；`LoginResult` 无 refreshToken 字段，且**后端返回字段为 snake_case `refresh_token`，前端按 camelCase 读取导致首次登录把字面 "undefined" 写入 localStorage**（这是续期彻底失效的直接原因）。
- 修复（前端，`apps/admin`）：
  - `api/auth.ts`：`LoginResult` 增 `refreshToken`；新增 `refreshToken(refresh_token)` 调 `/auth/refresh`；登录/刷新响应经 `mapLoginResult` 把 `refresh_token` 映射为 `refreshToken`（消除 "undefined" 缺陷）；
  - `stores/auth.ts`：登录持久化 `admin_refresh_token`，`reset()` 一并清理；
  - `utils/request.ts`：401 拦截器改为「先静默 refresh（单飞，并发 401 只发一次）→ 更新本地 token/refresh_token/user/permissions → 重放原请求；refresh 失败才清会话跳登录」；`/auth/refresh` 与登录请求自身不递归。
- 后端：`config.go` 默认 TTL 保持 900s 未动（仅注释说明），**运行时以 `ACCESS_TOKEN_TTL=7200` 环境变量覆盖为 2 小时**（后端启动命令需携带该 env）。
