## 0. 契约冻结机制（后端侧自证，2026-10-26）

- **冻结对象**：`/api/app/*` 的 64 个端点（方法 + 路径形状）、响应外层四键、`body` 内全部键名风格、金额字段路径清单。
- **基线文件**（随代码提交，diff 就是评审面）：
  - `internal/integration/testdata/app_routes.txt` —— 64 行 `METHOD /path`，由 gin 运行时路由表导出，不是手抄清单，因此不可能与代码不同步。
  - `internal/integration/testdata/app_money_fields.txt` —— 41 条 `METHOD /path -> body.字段路径`，按真实响应走出来。
- **守护用例**（`internal/integration/app_contract_test.go`）：
  - `TestAppRouteContractBaseline`：新增/删除/改名 App 端点即失败，输出「基线有而代码没有 / 代码新增而基线没有」两类差异。
  - `TestAppResponseKeysAreSnakeCase`：外层必须恰好是 `code`/`message`/`body`/`request_id`；`body` 内所有键必须匹配 `^[a-z][a-z0-9_]*$`。覆盖 23 个只读端点 + 3 个订单详情端点。
  - `TestAppMoneyFieldBaseline`：金额字段路径清单变化即失败，供 R2-6（元 float → 分 int）迁移逐条核对。
- **重新生成基线**：`go test ./internal/integration/ -count=1 -run "TestAppRouteContractBaseline|TestAppResponseKeysAreSnakeCase|TestAppMoneyFieldBaseline" -update=true`。注意 `-update` 要写在包路径**之后**且带 `=true`，否则 `go test` 会把它当包参数吞掉，报 `no Go files`。
- **变更流程**：改端点或字段 → 用例变红 → 确认三端影响 → 带 `-update=true` 重生成 → 基线 diff 与代码改动进同一次提交。契约变更因此只能显式发生。
- **金额字段现状**：14 个字段名 `amount`(6) `delivery_fee`(5) `price`(4) `packing_fee`(4) `pay_amount`(3) `month_income`(3) `min_price`(3) `balance`(3) `today_income`(2) `start_fee`(2) `goods_amount`(2) `discount_amount`(2) `red_packet_balance`(1) `fee`(1)，当前全部是元、float64 序列化，具体挂在哪些响应路径上以基线文件为准。
- **覆盖边界（诚实记录，别当成全量契约测试）**：
  - 探针只走 GET 只读端点，外加一个现造的订单（下单→支付→接单→备餐→抢单）用于三端订单详情；**POST/PUT 的请求体字段名不在校验范围内**，写接口字段漂移仍要靠 DTO 白名单与业务用例。
  - 列表端点为空时金额清单会少几行；用例里现造订单正是为了让清单不受种子数据影响。
  - 后台面（`/api/*`）不在本冻结范围内，且实测同一响应里大小写混用（`pageSize` 与 `created_at` 并存），属已知不一致，本次未改动。
- **版本状态**：本文件仍是 v0.1 草案。上面这套机制解决的是「后端说的和后端做的不一致」，升 v1.0 冻结仍需三端确认后按文件头约定递增版本号。

## 0. 通用约定

### 0.1 地址与环境

| 项 | 值 |
|---|---|
| 本地后端 | `http://127.0.0.1:8080` |
| Android 模拟器 | `http://10.0.2.2:8080`（`BuildConfig.API_BASE_URL`） |
| 前缀 | `/api/app/client`、`/api/app/store`、`/api/app/driver`、`/api/app/common` |
| 传输 | JSON UTF-8；`Content-Type: application/json`；上传为 `multipart/form-data` |
| 时区 | 服务端存 UTC；时间字段为 int64 Unix 秒，由客户端本地化 |

### 0.2 统一响应

沿用现有信封（`internal/pkg/response/response.go`）：

```json
{
  "message": "ok",
  "body": { },
  "request_id": "M5RW4NSYFQZ5V9P89PD5PEG74W",
  "code": 0
}
```

- `code == 0` 成功；非 0 为业务错误，`message` 可直接展示（后端已做中文文案）。
- HTTP 状态与 `code` 同时正确：400 参数、401 未认证、403 无权限、404 不存在、409 状态冲突、413 请求体超限、429 限流、500 内部错误。
- 每个响应带 `X-Request-ID`；客户端应回传 `X-Request-ID` 便于排障（现有 `ApiClient` 已生成）。
- **请求体上限**：非上传接口 1MB，超出返回 HTTP 413 + `code=1303`「请求体超过大小限制」；上传接口（`POST /api/uploads`、`POST /api/app/common/uploads`）放宽到 `STORAGE_MAX_SIZE_MB`（默认 10MB）。
- **参数错误文案**：绑定/校验失败只返回「请求参数错误」（`code=1301`），底层解析细节仅入服务端日志，客户端不要依赖 message 做分支，一律按 `code` 判断。

### 0.3 认证与会话

| 项 | 约定 |
|---|---|
| 认证头 | `Authorization: Bearer <access_token>` |
| access TTL | 默认 900s（可由 `ACCESS_TOKEN_TTL` 覆盖） |
| refresh | `POST /api/auth/refresh`，body `{"refresh_token":"..."}`，返回与登录相同信封 |
| 401 处理 | 客户端**单飞**刷新：并发 401 只发一次 refresh；成功则重放原请求；失败才清会话跳登录 |
| 刷新失败 | `1006`；客户端必须清 token，不得循环重试 |
| 登录/登出 | 复用 `/api/auth/login`、`/api/auth/sms/*`、`/api/auth/logout`、`/api/auth/me` |

> 前置修复：短信自动注册用户无 `credential` 行，导致登录后全部 401/1006（见审阅文档 §4.1）。**M0 必须先修**。

### 0.4 分页、排序、时间、金额

- 分页参数：`page`（默认 1）、`page_size`（默认 20，最大 100）。
- 分页响应：

```json
{ "list": [], "total": 0, "page": 1, "page_size": 20, "has_more": false }
```

> 后台面沿用 `pageSize`，App 面统一 `page_size`；两套命名空间互不影响，勿混用。

- 排序：默认 `created_at desc`；需要时用 `sort=created_at|distance|amount`。
- 时间：全部 int64 秒；客户端负责格式化为「今天 12:35」「10-25 12:35」。
- 金额：**float64 元，保留 2 位小数**（与现有库表一致）。服务端在计价与落库时统一四舍五入到分；客户端展示 `¥12.30` 格式。长期迁移整数分见审阅文档 §11。

### 0.5 幂等与并发

| 场景 | 机制 |
|---|---|
| 下单 | 请求头 `Idempotency-Key`（客户端生成 UUID）或 body `client_order_no`；DB 唯一索引 `(user_id, client_order_no)`；重复请求返回首次结果，不重复建单 |
| 支付 | `payments` 以 `order_id + channel` 幂等；重复支付返回已有支付单 |
| 抢单 | 单条条件更新：`UPDATE orders SET rider_id=?, status='待取货' WHERE id=? AND rider_id='' AND status IN (...)`；0 行 → `409/1801` |
| 状态流转 | 每次更新带 `WHERE status = 期望旧状态`；0 行 → `409/1607` |
| 库存/优惠券 | 条件更新；库存不足 → `1601`；券已用 → `1605` |

### 0.6 字段命名

- App 面**全部 `snake_case`**（含请求体、响应体、查询参数）。
- 枚举值：
  - 展示态 `status`：中文（兼容后台）。
  - 机器态 `status_code`：英文小写下划线（App 只对 `status_code` 做分支）。
- 布尔：`is_*` / `has_*`；数量：`*_count`；金额：`*_amount`；时间：`*_at`。

### 0.7 错误码分配

保留既有 `1001-1516`，新增 App 段：

| 段 | 含义 | 示例 |
|---|---|---|
| 12xx | 权限/主体 | `1202` 账号未绑定商家/骑手；`1203` 角色不符 |
| 16xx | 用户端交易 | `1601` 商品不存在/下架；`1602` 商家休息中；`1603` 金额校验失败；`1604` 地址不存在；`1605` 优惠券不可用；`1606` 超出配送范围；`1607` 状态不允许；`1608` 重复提交；`1609` 未选择服务区域 |
| 17xx | 商家端 | `1701` 菜品不存在；`1702` 分类不存在；`1703` 资源不属于本店；`1704` 菜品在售不可删 |
| 18xx | 骑手端 | `1801` 订单已被抢；`1802` 骑手未上线；`1803` 超出接单范围；`1804` 取送校验失败 |
| 19xx | 资金 | `1901` 支付失败；`1902` 余额不足；`1903` 提现金额超限；`1904` 提现次数超限；`1905` 结算单不存在 |
| 13xx | 通用补充 | `1303` 文件过大；`1304` 文件类型不支持 |

完整错误码字典由后端在 `internal/pkg/errcode` 增补，并导出给三端共用。

### 0.8 角色、主体与守卫

| 命名空间 | 角色 | 主体绑定 | Casbin 资源 |
|---|---|---|---|
| `/api/app/client` | `user` | `users.region_id`（首次进入时设置，见 C01/C02） | `app_client:*` |
| `/api/app/store` | `merchant` | `users.merchant_id`（必须非空） | `app_store:*` |
| `/api/app/driver` | `driver` | `users.rider_id`（必须非空） | `app_driver:*` |
| `/api/app/common` | 以上任意 | 按角色 | `app_common:*` |

**计价规则（服务端权威）：**

```
goods_amount   = Σ(dish.price × count)                                       // 校验下架/库存
packing_fee    = merchant.packing_fee                                         // 按单收取
delivery_fee   = merchant.delivery_fee（未配置则 region.start_fee + 超里程费，超里程单价需新增配置）
discount_amount= coupon（满足 min_spend 且未过期）/ 活动
pay_amount     = max(0, goods_amount + packing_fee + delivery_fee - discount_amount)
```

**校验顺序与错误：**

1. 区域/商家营业/配送范围 → `1602` / `1606`
2. 菜品存在、在售、库存 → `1601`
3. 地址归属 → `1604`
4. 优惠券 → `1605`
5. 幂等键重复 → 返回首次订单（不报错）
6. 客户端金额与服务器不一致 → 忽略客户端金额（不报错，以服务端为准；日志告警）

**副作用：** 建单（`待支付`）+ 写 `order_events` 在同一事务内；库存扣减与优惠券锁定建议在**支付成功时**执行（待支付超时释放），避免未支付订单占用库存。

### 4.2 上下线

`PUT /api/app/driver/status`：`{"online": true}` → `{status:"在线",status_code:"online",accepting:true}`。

- 下线时若有进行中订单，仍可完成取送，但不再进入抢单池。
- 冻结（`frozen`）骑手登录可查看历史，但不能上线/抢单（`1802`）。

### 4.3 抢单池

`GET /api/app/driver/order-pool?lat=30.42&lng=115.33&type=外卖&page=1&page_size=20`

```json
{
  "list": [
    {
      "order_id": "SG202610250001",
      "order_no": "202610250001",
```

### 4.4 抢单 / 取货 / 送达

`POST /api/app/driver/orders/{id}/grab`：无 body。

```json
{
  "order": { "id": "SG202610250001", "status": "待取货", "status_code": "ready" },
  "pickup_code": "1234",
  "delivery_code": "5678"
}
```

- 已下线 → `403/1802`；已被抢 → `409/1801`；超出区域/类型 → `403/1803`。
- 抢单成功：`rider_id` 写入、状态保持 `待取货`、`accepted_at` 记录、写事件、通知用户「骑手已接单」。

`POST /api/app/driver/orders/{id}/pickup`：

```json
{ "pickup_code": "1234", "photo_url": "" }
```

- 仅接单骑手、状态 `待取货` → `配送中`；记录 `picked_at`；开始位置追踪；返回订单。
- 校验码错误 → `400/1804`（如商家启用出餐码）。

`POST /api/app/driver/orders/{id}/deliver`：

```json
{ "delivery_code": "5678", "photo_url": "" }
```

- 仅接单骑手、状态 `配送中` → `已送达`；记录 `delivered_at`；计算 `rider_earning`；通知用户确认收货。
- 送达后用户未确认：N 小时后自动确认（cron），进入 `待评价`。

### 4.5 位置上报

`POST /api/app/driver/location`

```json
{ "lat": 30.4252, "lng": 115.3318, "heading": 87.5, "speed": 18.2, "accuracy": 8.0, "ts": 1792900800 }
```

- 频率限制：1 次/2 秒（超出返回 429，不阻断业务）。
- 服务端：写 `rider_locations`（upsert）+ Redis `GEOADD geo:rider:<region>`，供抢单池距离排序与追踪使用。
- 仅在 `online` 或存在进行中订单时接受上报，避免无意义写入。

### 4.6 收入与提现

- `GET /finance/summary` → `{balance, today_income, month_income, today_orders, month_orders, withdrawable}`

- `POST /withdrawals` → 同商家端，按提现规则校验；骑手需已实名、已绑定银行卡/微信。

## 5. 订单状态机（跨三端唯一口径）

### 5.1 状态表

| `status`（中文入库） | `status_code` | 含义 | 可执行方 |
|---|---|---|---|
| 待支付 | `pending_pay` | 已创建未支付 | 用户：pay/cancel |
| 待接单 | `pending_accept` | 已支付等商家 | 商家：accept/reject；用户：cancel（限时） |
| 备餐中 | `preparing` | 商家已接单 | 商家：ready |
| 待取货 | `ready` | 出餐完成，等骑手 | 骑手：grab |
| 配送中 | `delivering` | 骑手已取货 | 骑手：deliver |
| 已送达 | `delivered` | 骑手已送达 | 用户：confirm；系统：自动确认 |
| 待评价 | `pending_review` | 已确认待评价 | 用户：review；系统：超时转已完成 |
| 已完成 | `completed` | 评价完成/评价期结束 | — |
| 已取消 | `canceled` | 取消/拒单/超时 | — |
| 退款售后 | `after_sale` | 售后处理中 | 商家/平台：decision |
| 已退款 | `refunded` | 退款完成 | — |
| 异常 | `abnormal` | 出餐超时/配送异常 | 平台处理 |

> 兼容：历史数据 `已取件待送达` 迁移为 `配送中`；`出餐超时` 迁移为 `abnormal` 并写 `abnormal_reason=出餐超时`。后台 UI 的中文映射保持不变。

### 5.2 流转表

| 从 | 到 | 触发 | 接口 | 守卫条件 | 副作用 |
|---|---|---|---|---|---|

### 8.3 冒烟链路（契约冻结后执行）

```powershell
$base = 'http://127.0.0.1:8080/api'
# 1) 用户登录
$u = irm -Method Post "$base/auth/sms/send" -ContentType application/json -Body '{"phone":"13800008640"}'
$u = irm -Method Post "$base/auth/sms/login" -ContentType application/json -Body (@{phone='13800008640';code=$u.body.dev_code} | ConvertTo-Json -Compress)
$uh = @{ Authorization = "Bearer $($u.body.token)" }
# 2) 商家/菜单
irm "$base/app/client/merchants?page=1&page_size=10" -Headers $uh
irm "$base/app/client/merchants/M00268" -Headers $uh
# 3) 地址 + 下单 + 支付
irm -Method Post "$base/app/client/orders" -Headers $uh -ContentType application/json -Body '{...}'
irm -Method Post "$base/app/client/orders/$id/pay" -Headers $uh -ContentType application/json -Body '{"channel":"balance"}'
# 4) 商家接单/出餐（商家 token）
irm -Method Post "$base/app/store/orders/$id/accept" -Headers $sh
irm -Method Post "$base/app/store/orders/$id/ready"  -Headers $sh
# 5) 骑手抢单/取货/送达（骑手 token）
irm "$base/app/driver/order-pool" -Headers $dh
irm -Method Post "$base/app/driver/orders/$id/grab"   -Headers $dh
irm -Method Post "$base/app/driver/orders/$id/pickup" -Headers $dh -ContentType application/json -Body '{"pickup_code":"1234"}'
irm -Method Post "$base/app/driver/orders/$id/deliver" -Headers $dh -ContentType application/json -Body '{"delivery_code":"5678"}'
# 6) 用户确认 + 评价
irm -Method Post "$base/app/client/orders/$id/confirm" -Headers $uh
irm -Method Post "$base/app/client/orders/$id/review"  -Headers $uh -ContentType application/json -Body '{"rating":5,"tags":["味道好"]}'
```

验收断言：每一步 `code=0`；订单最终 `status_code=completed`；`order_events` 覆盖 8 个节点；并发抢单仅 1 个 200、其余 409/1801。
