# 系统内置 System 身份设计分析

> 项目：曙光跑腿 SaaS 多租户外卖跑腿（dawn-errand） 
> 适用范围：后端身份权限限界上下文（`internal/domain/identity`、`internal/application/system`、Casbin 权限体系）
> 文档状态：设计分析 / 待评审

---

## 1. 背景与设计目标

平台在运行时存在大量"机器发起"的操作：发送验证邮件、触发短信通知、投递站内信、执行系统定时任务（如提现审核、结算、区域策略刷新）。这些操作过去通常被实现为"无主调用"——直接调用基础设施接口、不留操作者、不进审计，导致三个问题：

1. **无法审计归因**：一封邮件、一条站内信由"谁"发出无从追溯；
2. **权限体系旁路**：系统调用绕过 RBAC 与数据隔离，等于隐性超管入口；
3. **身份模型割裂**：人工用户走 users 表，系统进程走"魔法函数"，出现两套并行的身份处理逻辑。

本设计的目标：**把系统进程纳入统一身份模型**。在系统初始化完成后，自动创建 4 个系统级身份——**邮件服务系统、短信服务系统、站内信通知服务系统、基础系统服务**，它们与自行注册的用户一样，拥有 users 表的基础用户信息（ID、邮箱、昵称、状态、角色等），以普通用户的形态存在，但承载"系统级调用方"的职责。

## 2. 方案定义

### 2.1 内置系统身份清单

| 身份 | 定位 | 典型职责 | 建议标识 |
|---|---|---|---|
| 邮件服务系统 | 邮件通道 | 发送验证邮件、重置邮件、通知邮件 | `mailer@system.shuguang` |
| 短信服务系统 | 短信通道 | 发送验证码、订单通知、营销触达 | `sms@system.shuguang` |
| 站内信通知服务系统 | 站内通知 | 站内信投递、消息中心、公告推送 | `inmail@system.shuguang` |
| 基础系统服务 | 平台基础能力 | 定时任务、结算、数据清扫、策略刷新 | `system@shuguang.local` |

### 2.2 生命周期

```
migrate up（建表）
   │
   ▼
seed（幂等种子：区域/超管/费率/公告…）
   │
   ▼
POST /api/system/bootstrap（幂等初始化）
   ├─ 创建超管 + 默认 Casbin 策略 + 默认配置
   └─ 同步创建 4 个系统身份（EnsureSystemUsers，幂等）
   │
   ▼
系统服务上线（邮件/短信/站内信/定时任务以系统身份调用业务接口）
```

要点：
- **随初始化创建**：`bootstrap` 完成（`MarkInitialized` 置位）即视为"系统就绪"，在同一事务/流程内创建系统身份，保证初始化完成即存在、不依赖人工；
- **幂等**：重复执行不重复创建（按固定邮箱/标识查找存在则跳过），与现有 bootstrap 幂等语义一致；
- **不可登录**：系统身份不设密码（`credentials` 表不落记录或存不可用标记），彻底杜绝密码登录路径。

### 2.3 数据模型（贴合现有 users 表）

系统身份复用 `users` 表基础字段（与自行注册用户一致）：`id / email / phone / name / avatar / status / email_verified / role / registered_at / updated_at`。

角色取值建议新增 `RoleSystem = "system"`（区别于现有 7 种业务角色），并通过 `user_kind` 语义或角色 + 固定邮箱规则区分"系统身份"与普通用户。系统身份的租户绑定字段（`region_id / merchant_id / rider_id`）保持为空，**Scope 恒为 Global**，不归属任何区域/商家/骑手。

## 3. 合理性分析

### 3.1 复用统一用户模型，消除"特例代码"

当前架构的身份载体只有一个：`identity.User` 聚合根 + `credentials` 凭证 + Casbin 角色 + 审计记录。若系统进程走独立表（如 `system_accounts`），则：

- 鉴权中间件要开第二套分支（"这个 token 是系统 token 还是用户 token"）；
- 审计、消息、前端展示各自都要处理"非用户"；
- 每新增一类系统能力就要加一张表或一套逻辑。

**复用 users 表**后，系统身份就是一条普通 user 记录，中间件、DTO、审计、消息路由全部零特例。这是对"以统一身份模型承载一切调用方"这一原则的直接落实。

### 3.2 审计与归因闭环

现有 `audit_logs` 以 `user_id / action / object / result / request_id / ip` 记录敏感操作。系统身份入表后：

- 邮件/短信/站内信的发送方可以填系统身份 `user_id`，**每条触达可追溯到具体系统组件与时间**；
- 定时任务（结算、审核）的 operator 不再是空值，而是"基础系统服务"；
- 排查故障、合规取证（谁在什么时间发了什么）有据可查。

### 3.3 权限体系自然复用，不增加旁路

系统服务调用业务接口时携带系统身份的访问凭证，中间件照常走：

- **Casbin `RequirePerm(obj, act)`**：给 `system` 角色精确授权（如 `notification:send`、`settlement:run`），而不是放开 `*`；
- **数据隔离 Scope**：系统身份恒为 Global，平台级任务可见全量数据，但**对象级操作仍受 application 层二次校验**约束，不会获得"隐形超管"特权；
- **限流/审计中间件**：与普通请求同一条管道，行为可观测。

这样"系统能做什么"由策略表明文可见、可审计、可收权，而不是散落在代码深处的隐藏调用。

### 3.4 与多租户隔离模型一致

项目的数据安全按 `Scope(Global/RegionID/MerchantID/RiderID/UserID)` 在仓储层强制隔离。系统身份归属 Global、不绑定任何租户，天然符合"平台级服务不属任何租户"的边界，不会污染商户数据可见性；同时站内信投递以普通用户为收件人，系统身份作为发件人，与消息模型（sender → receiver 均为 user_id）完全兼容。

### 3.5 幂等初始化链路成熟

现有 `bootstrap` 已实现幂等（已初始化返回 1102）、事务化（失败不标记初始化）、审计留痕。系统身份创建挂在该链路上：

- 不需要新增初始化接口或第二套启动编排；
- 与"超管 + 默认策略 + 默认配置"同一生命周期，语义一致；
- 重复调用、并发调用均有既有机制兜底。

### 3.6 前端与业务可读性

- 管理后台的用户列表、审计列表可直接展示"邮件服务系统""短信服务系统"等具名主体，运营可理解、可排查；
- 站内信/消息中心天然需要"系统"作为发件人身份，前端无需为系统消息发明新的展示分支。

## 4. 好处汇总

| 维度 | 收益 |
|---|---|
| 架构一致性 | 唯一身份模型（users），无第二套系统账号代码路径 |
| 可审计性 | 所有机器操作可归因到具体系统身份与时间戳 |
| 安全性 | 系统能力进入 Casbin 策略面，可授权/可收权，杜绝旁路超管 |
| 数据隔离 | Global Scope 与租户边界天然一致，不污染商户数据 |
| 可维护性 | 新增系统服务 = 加一条种子身份 + 策略，无需改框架 |
| 初始化一致性 | 随幂等 bootstrap 自动创建，完成即就绪 |
| 前端/运营友好 | 消息、审计、用户列表以具名身份呈现 |

## 5. 风险、边界与实现注意

| 风险 | 说明与对策 |
|---|---|
| 系统身份被用于登录 | **必须禁登录**：不创建密码凭证（credentials 无记录），登录服务按无凭证直接拒绝；即使被猜测密码也不存在比对对象 |
| 系统 token 泄漏 | 系统身份访问凭证只允许在服务内部签发（如通过专用内部密钥/短 TTL），不得出现在前端、日志与配置明文；泄露后按身份撤销并轮换 |
| 授权过宽 | 策略只给 `system` 角色最小必要权限（`notification:send`、`settlement:run` 等），**禁止**授予 `*` 或 super_admin 能力 |
| 与真实运营账号混淆 | 通过固定邮箱后缀（`*@system.shuguang`）+ `role=system` 双标记识别；前端列表加"系统"标签；禁止人工操作借用系统身份 |
| 审计盲区 | 系统调用也走中间件与审计记录，operator 填系统身份 user_id；不得在 infrastructure 层直接"裸调"绕过 |
| 邮箱唯一约束 | 系统身份邮箱占用 users 表唯一约束，需保证注册路由能拒绝同名注册（与现有唯一性逻辑一致） |
| 幂等创建竞态 | EnsureSystemUsers 按固定标识（邮箱）先查后建，配合唯一约束 + 冲突吞错，保证并发下不重复 |
| 封禁误伤 | 系统身份 status 不得被运营封禁接口操作；给 `system` 角色在 user:ban 策略上明确拒绝 |

## 6. 实现建议（贴合当前代码）

1. **常量**：`internal/domain/identity/identity.go` 增加 `RoleSystem = "system"` 与系统身份邮箱常量清单（4 条）；
2. **初始化**：`internal/application/system/service.go` 的 `Bootstrap` 在创建超管后调用 `EnsureSystemUsers(ctx, tx)`——按固定邮箱 `Get` → 不存在则 `Save`（`EmailVerified=true`、`Role=RoleSystem`、`Status=active`、无 credential），事务内完成、失败回滚；
3. **种子兜底**：`cmd/seed` 同样执行 EnsureSystemUsers，保证未走 bootstrap 的开发环境也有系统身份；
4. **凭证**：系统身份不写 `credentials` 行；如需服务间调用凭证，另走内部短 TTL 签名通道，不落密码；
5. **策略**：`internal/infrastructure/casbin` 默认策略增加 `p, system, <obj>, <act>` 最小权限行（如通知/结算类），并在 `user:ban` 等对象上显式拒绝；
6. **DTO/前端**：用户列表/审计 DTO 对 `role=system` 输出"系统"标签；`Login` 对 system 身份返回 1002（无凭证即不可登录，天然生效）；
7. **隔离**：Scope 派生中 `system` 角色归入 Global 分支，`region_id/merchant_id/rider_id` 恒为空；
8. **文档同步**：OpenAPI/错误码说明中补充系统身份说明与"禁登录、禁越权"约束。

## 7. 结论

将邮件、短信、站内信与基础系统服务建模为 **users 表中的系统级身份、随初始化幂等自动创建**，是该平台身份模型下**一致性最高、审计最完整、扩展成本最低**的方案：

- 不引入第二套账号体系，避免"特例分支"腐蚀架构；
- 让系统能力显式进入权限面与审计面，而非隐藏旁路；
- 与幂等初始化、多租户 Scope 隔离、统一返回结构等既有约束无缝衔接。

建议按 §6 落地；评审重点放在 **§5 的登录禁令、最小授权与 token 安全**三项。
